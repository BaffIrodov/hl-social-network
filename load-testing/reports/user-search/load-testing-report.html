Влияние индексов на поиск анкет

Методология

Стенд: Java 21, Spring Boot 4.1.1, Spring JDBC, PostgreSQL 17.11 и Gatling 3.16.0. Приложение запущено через Run в IDEA; БД — в Docker. Всё работает на одном ПК: Ryzen 7 3700X, 8 ядер / 16 потоков, 32 ГиБ RAM. Пул HikariCP: максимум 10 соединений, минимум 2 свободных, ожидание до 5000 мс.

В базе 1 000 000 анкет. За основу был взять список OTUS (csv-файл, приложенный к домашнему заданию). В нем выделены 138 уникальных имён и 1006 фамилий. По этому списку далее были созданы случайные анкеты, имена и фамилии выбирались равновероятно. Возраст при генерации — 20–50 лет. Данные между замерами не менялись.

Далее проверялся вот такой запрос:

GET /user/search?first_name=Ив&second_name=Ив

Далее было выбрано 5 кандидатов-индексов:

  1. b-tree (сначала имя, затем фамилия, используется varchar_pattern_ops. Короткий пример: first_name varchar_pattern_ops, second_name varchar_pattern_ops);
  2. b-tree (сначала фамилия, затем имя, используется varchar_pattern_ops. Короткий пример: second_name varchar_pattern_ops, first_name varchar_pattern_ops);
  3. Два отдельных b-tree (отдельно фамилия, отдельно имя, используется varchar_pattern_ops. Короткий пример: first_name varchar_pattern_ops, затем: second_name varchar_pattern_ops);
  4. B-tree только по фамилии (отдельно фамилия, используется varchar_pattern_ops. Короткий пример: first_name varchar_pattern_ops);
  5. GIN с pg_trgm (сначала фамилия, затем имя. Короткий пример: USING gin (first_name public.gin_trgm_ops, second_name public.gin_trgm_ops));

Сначала для всех кейсов проверены результаты explain. Затем проведено нагрузочное тестирование при нагрузке 100 клиентов × 60 секунд. Перед каждой конфигурацией — прогрев 1 клиент × 30 секунд.

По результатам этого нагрузочного тестирования был выбран индекс "B-tree: фамилия → имя". Для него выполнена финальная серия: 1, 10, 100, 1000 клиентов, по 120 секунд на уровень. Перед всей серией — один прогрев 1 × 30 секунд.

Запуск из load-testing/gatling: gatling:test -Dusers=N -Dduration=120. RPS и latency взяты из итоговой таблицы Gatling; время SQL — из EXPLAIN.

Разница объясняется вариативностью данных фамилий и имен: фамилии более уникальные. Префикс фамилии отбирает 1978 анкет, имени — 7220. Более избирательная фамилия стоит первой и сужает ведущий диапазон B-tree.

Графики

До индекса: сохранена предыдущая серия от 31.10.2026 — три замера по 120 секунд на уровень. После индекса: новая серия от 01.11.2026 — один замер по 120 секунд на уровень для «фамилия → имя». Число анкет и параметры пула те же; число повторов различается.

Вывод

Для выбранных префиксов лучший результат дал составной B-tree «фамилия → имя». В сравнении 100 × 60 он увеличил успешный throughput примерно в 45 раз относительно базы без поискового индекса. В финальной серии при 1000 клиентах получено 3693,83 запроса/с, p95 — 329 мс. Переход от 100 к 1000 клиентам почти не изменил throughput, но увеличил среднюю задержку с 26 до 266 мс. Выбор относится к этому стенду и сочетанию префиксов; для других запросов порядок колонок может оказаться менее выгодным.

Во всех измерениях сохранён миллион исходных анкет.

Порядок работы

  1. В DataGrip выберите подключение к social_network_load.
  2. Дождитесь завершения нагрузки и выполните один SQL-файл целиком.
  3. Проверьте выведенный список индексов: users_pkey и индексы выбранного варианта.
  4. Выполните explain.sql для базового варианта и каждого из пяти кандидатов. Первый запуск прогревает данные, второй полный план сохраняется для отчёта.
  5. Для предварительного сравнения отдельно запускайте gatling:test -Dusers=100 -Dduration=60. Полную серию 1/10/100/1000 выполняйте только для выбранного победителя.

Каждый файл в одной транзакции проверяет имя базы, удаляет известные поисковые индексы этого набора, создаёт выбранный вариант и выполняет ANALYZE public.users. Анкеты и первичный ключ сохраняются. При ошибке транзакции выполните ROLLBACK.

Ручное нагрузочное тестирование /user/search

Ручное нагрузочное тестирование /user/search

Gatling 3.16.0, Java 21, Maven Wrapper. Один запуск проверяет один уровень нагрузки. Приложение и PostgreSQL запускаются отдельно; приложение подключается к social_network_load. Данные: миллион анкет.

Запуск в IDEA

Создайте конфигурацию Run → Edit Configurations → + → Maven:

  • Working directory: C:\Users\serge\Desktop\hl-social-network\load-testing\gatling.
  • JRE: Java 21.
  • Command line:
gatling:test -Dusers=100 -Dduration=60

Сценарий UserSearchSimulation выбран в pom.xml, в папке load-testing.

Приложение запускайте через Run, с включённым Disable launch optimization. Для прогрева выполните gatling:test -Dusers=1 -Dduration=30.

Параметры

Параметр По умолчанию Значение
users 1 Число одновременно работающих клиентов
duration 60 Длительность подачи нагрузки, секунды
baseUrl http://localhost:8880 Адрес приложения
firstName Ив Префикс имени
secondName Ив Префикс фамилии

Каждый клиент выполняет один GET /user/search, затем заменяется следующим. Пауз между запросами нет.

Данные для нагрузочных тестов

Для поиска генерируем 1 000 000 анкет SQL-скриптом. Нужен Docker с Compose v2. Команды выполняются из корня проекта.

Запуск с отдельной базой

Запустите PostgreSQL:

docker compose up -d db

Один раз создайте базу для нагрузки:

docker compose exec db createdb -U postgres social_network_load

Если база уже существует, повторять эту команду не нужно.

Подключите словарь и SQL-скрипт к контейнеру и переключите приложение на нагрузочную базу:

docker compose -f compose.yaml -f load-testing/compose.load.yaml up --build -d
docker compose logs -f app

Дождитесь Started SocialNetworkApplication, затем выйдите из просмотра логов через Ctrl+C. Liquibase автоматически создаст таблицы. API доступен на http://localhost:8880.

Словарь и генерация

В profile-names.json сохранены все уникальные имена и фамилии из исходного CSV OTUS: 138 имён и 1006 фамилий.

Каждая анкета получает:

  • случайное имя и фамилию из отдельных списков, с одинаковой вероятностью выбора;
  • случайную дату рождения: полный возраст от 20 до 50 лет включительно на день генерации;
  • случайный пол MALE или FEMALE, с одинаковой вероятностью выбора;
  • biography=null, city=null.

Запустите генератор:

docker compose -f compose.yaml -f load-testing/compose.load.yaml exec -T db psql -U postgres -d social_network_load -f /load/generate-profiles.sql

Команда создаем/заменяет существующие анкеты только в social_network_load.

Генерация выполняется одной транзакцией. После неё обновляется статистика командой ANALYZE users. При повторном запуске набор будет новым; размер задаётся константой profile_count в generate-profiles.sql.

Проверка

docker compose exec db psql -U postgres -d social_network_load -c "SELECT count(*) FROM users;"

Ожидаемый результат — 1000000. В Postman выполните запрос поиска с префиксами Ив и Ив. Интеграционные тесты используют social_network_test и не очищают нагрузочную базу.

Чтобы вернуть приложение к обычной базе:

docker compose up -d

-- Заменяет тестовые анкеты только в базе social_network_load.

\set ON_ERROR_STOP on



BEGIN;

SET LOCAL TIME ZONE 'Europe/Moscow';



DO $$

DECLARE

    profile_count constant integer := 1000000;

    birthdate_from constant date := (CURRENT_DATE - INTERVAL '51 years')::date + 1;

    birthdate_to constant date := (CURRENT_DATE - INTERVAL '20 years')::date;

    dictionary jsonb;

    first_names text[];

    second_names text[];

BEGIN

    IF current_database() <> 'social_network_load' THEN

        RAISE EXCEPTION 'Run this script only in social_network_load';

    END IF;



    dictionary := pg_read_file('/load/profile-names.json')::jsonb;

    SELECT array_agg(value) INTO first_names

    FROM jsonb_array_elements_text(dictionary -> 'first_names');

    SELECT array_agg(value) INTO second_names

    FROM jsonb_array_elements_text(dictionary -> 'second_names');



    IF COALESCE(cardinality(first_names), 0) = 0 OR COALESCE(cardinality(second_names), 0) = 0 THEN

        RAISE EXCEPTION 'Both name lists must be nonempty';

    END IF;

    IF EXISTS (

        SELECT 1 FROM unnest(first_names || second_names) AS names(value)

        WHERE value IS NULL OR btrim(value) = '' OR char_length(value) > 100

    ) THEN

        RAISE EXCEPTION 'Names must contain between 1 and 100 characters';

    END IF;



    TRUNCATE users, user_credentials, user_sessions RESTART IDENTITY;



    INSERT INTO users (first_name, second_name, birthdate, gender)

    SELECT

        first_names[1 + floor(random() * cardinality(first_names))::integer],

        second_names[1 + floor(random() * cardinality(second_names))::integer],

        birthdate_from + floor(random() * (birthdate_to - birthdate_from + 1))::integer,

        CASE WHEN random() < 0.5 THEN 'MALE' ELSE 'FEMALE' END::user_gender

    FROM generate_series(1, profile_count);



    RAISE NOTICE 'Generated % profiles; birthdates from % to %',

        profile_count, birthdate_from, birthdate_to;

END $$;



COMMIT;

ANALYZE users;



SELECT count(*) AS profiles, min(birthdate) AS first_birthdate, max(birthdate) AS last_birthdate

FROM users;
