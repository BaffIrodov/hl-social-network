Репликация PostgreSQL

Стенд и маршрутизация

В Docker Compose запущены один primary и две физические реплики PostgreSQL 17.11, replica1 и replica2. У каждого узла свой том. Обе реплики асинхронно получают изменения от primary через поток WAL.

Для GET /user/get/{id} и GET /user/search приложение по очереди выбирает одну из двух реплик. Запросы регистрации и входа идут на primary.

Базовые замеры и чтение с реплик

Оба стенда использовали 1 000 000 анкет с ID от 1 до 1 000 000. Контрольная сумма анкет совпала на всех узлах. В режиме с одной БД настроены 10 соединений, в режиме с репликами - по 5 соединений на реплику.

Приложение работало в Docker на Java 21. Замеры выполнены в Gatling 3.16.0. Каждый API прогревался одним клиентом 30 секунд, затем тестировался со 100 одновременными клиентами в течение 60 секунд. Каждый клиент выполнял один GET и сразу заменялся следующим.

  • /user/get/{id} выбирал ID из миллиона анкет.
  • /user/search искал по first_name=Ив&second_name=Ив. Запрос возвращал 14 анкет.

Отказ primary

Для каждого прогона запускали отдельный кластер. Четыре клиента записывали данные. После сбоя проверяли, какие из подтверждённых записей сохранились на новом primary.

В обоих режимах использовались synchronous_commit=on и fsync=on. В режиме async primary подтверждает запись после сохранения WAL на своём диске. В режиме ANY 1 (replica1, replica2) primary ждёт записи WAL на диск хотя бы одной реплики, прежде чем подтвердить коммит.

В первой паре прогонов остановили только primary. Во второй паре сначала по очереди отключили оба потока WAL, оставили клиентов под нагрузкой, затем остановили primary.

Переключение на новый primary

После сбоя сравнили позиции WAL и повысили реплику с более свежими данными. При равных позициях выбирали replica1. Вторую реплику подключили к новому primary. Затем сделали тестовую запись через SQL и проверили, что она появилась на второй реплике.
