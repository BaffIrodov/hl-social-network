Стенд и маршрутизация

В Docker Compose запущены один primary и две физические реплики PostgreSQL 17.11, replica1 и replica2. У каждого узла свой том. В primary перенесён набор данных одиночной БД. При первом запуске реплики получили его через pg_basebackup --wal-method=stream -R, затем начали получать WAL. На primary роль replicator подключается из подсети узла по SCRAM. Для обеих реплик pg_stat_replication показал streaming и async.

В Spring-профиле replication используется LazyConnectionDataSourceProxy. При первом SQL-запросе в транзакции readOnly = true приложение берёт соединение с одной из реплик по очереди. Так выполняются GET /user/get/{id} и GET /user/search. Регистрация и логин используют primary. Liquibase подключается к его пулу напрямую через @LiquibaseDataSource.

На временной базе того же кластера счётчики подтвердили запись анкеты, хэша пароля и сессии, чтение хэша при логине и выполнение миграций на primary. Анкета, сессия и шесть записей миграций появились на обеих репликах после применения WAL.

Базовые замеры и чтение с реплик

Оба стенда использовали 1 000 000 анкет с ID от 1 до 1 000 000 и индекс users_surname_name_prefix_idx на (second_name varchar_pattern_ops, first_name varchar_pattern_ops). Контрольная сумма анкет совпала на всех узлах. Одиночный пул допускал 10 соединений. В режиме с репликами лимит чтения составил по 5 соединений на узел.

Приложение работало в Docker на Java 21, Gatling 3.16.0 — на том же компьютере под Windows. Процессор Ryzen 7 3700X, Docker видел 16 логических процессоров и около 15,6 ГиБ памяти. Каждый API прогревался одним клиентом 30 секунд, затем тестировался со 100 одновременными клиентами в течение 60 секунд. Каждый клиент выполнял один GET и сразу заменялся следующим. Сценарии и параметры запросов совпадали на обоих стендах.

  • /user/get/{id} выбирал ID из миллиона анкет с seed 42. Gatling проверял HTTP 200 и ID в ответе.
  • /user/search искал по first_name=Ив&second_name=Ив. Запрос возвращал 14 анкет. Gatling проверял HTTP 200 и JSON-массив.

SQL по узлам

Для каждого прогона взята разница pg_stat_statements.calls между концом прогрева и концом замера. Сумма SQL-вызовов на репликах совпала с числом успешных HTTP-запросов.

Запросprimaryreplica1replica2

SQL для подсчёта запросов 
SELECT COALESCE(sum(calls) FILTER (WHERE query ILIKE '%FROM users WHERE id = %'), 0) AS get_calls,
       COALESCE(sum(calls) FILTER (WHERE query ILIKE '%WHERE first_name LIKE %'), 0) AS search_calls
FROM pg_stat_statements
WHERE dbid = (SELECT oid FROM pg_database WHERE datname = current_database())
  AND query ILIKE 'SELECT id, first_name, second_name,%';

Эксперименты с отказом primary

Для каждого прогона создан отдельный Compose-проект с primary и двумя репликами. Четыре JDBC-клиента вставляли по одному UUID на транзакцию в таблицу replication_write_probe. Клиент записывал UUID в журнал после успешного COMMIT. Потерянными считались подтверждённые UUID, отсутствовавшие на новом primary.

В обоих режимах использовались synchronous_commit=on и fsync=on. В async список synchronous_standby_names пуст. В режиме ANY 1 (replica1, replica2) primary ждёт записи WAL на диск хотя бы одной реплики, прежде чем подтвердить коммит.

В первой паре прогонов остановили только primary. В контрольной паре сначала по очереди отключили оба потока WAL через primary_conninfo, оставили клиентов под нагрузкой, затем остановили primary. Во всех четырёх случаях primary получил SIGKILL и завершился с кодом 137.

После фиксации разрыва обоих потоков async подтвердил ещё 3 167 записей. Все они вошли в число потерь. В контрольном прогоне ANY 1 все четыре клиента ждали в SyncRep и получили ноль подтверждений после разрыва. Для этого прогона таймаут чтения JDBC увеличен с 5 до 20 секунд, чтобы клиенты дождались аварийной остановки. В каждом прогоне четыре операции завершились с SQLSTATE 08006 без подтверждения коммита. Их UUID отсутствовали на новых primary.

Переключение на новый primary

Кандидат выбирался по максимальной позиции WAL, записанного на диск, с учётом позиции применённого WAL. При равных позициях выбиралась replica1. После pg_promote() вторую реплику подключили к новому primary. В режиме ANY 1 новый primary ожидал подтверждение от оставшейся реплики. Контрольный INSERT выполнился на новом primary, запись появилась на подключённой реплике.
